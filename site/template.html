Formalizing CPython

We modelled the reference Python interpreter in a proof assistant, one function at a time, tested every model against the real interpreter, and counted a function only after an independent reviewer agreed the model was faithful. Here is what that took, what it turned up, and how to do it for your own language.

Python is whatever CPython does

There is no formal specification of Python. The language reference describes the common case, and everything else is defined by what the reference implementation does: about half a million lines of C plus a standard library written in Python. The interesting behaviour lives in the corners. An __eq__ that mutates the dict being searched. A key whose __hash__ raises halfway through an insert. An integer one past sys.maxsize. A C fast path and a pure-Python twin that are supposed to agree and occasionally don't.

A proof assistant drags every one of those corners into the open. To state a theorem about range.__len__ you first have to write down what it does for a step of zero, for a length that doesn't fit in a C long, and for an argument whose __index__ returns a subclass of int. This project applies that discipline to CPython at scale. It follows Miles Cranmer's julia-in-lean, which modelled Julia Base in Lean 4 and found more than 400 bugs on the way1.

The work started on {{STARTED}}. It was done by Claude agents running in parallel under Claude Code, with a human setting direction and deciding what counts. Every heavy job (Lean builds, differential tests, reproducers) ran on our own build machine. Across {{COMMITS}} commits, {{MODELLED}} rows have been modelled, and {{FAITHFUL}} of them have survived independent review.

Mirror, then prove

Every model follows its source line by line: the same branch order, the same early returns, the same overflow behaviour, each step citing the 3.15.2 file and line. Below is the function that computes the length of a range on the C fast path, beside its Lean mirror. Point at a line to see its counterpart. The unsigned arithmetic is modelled exactly, wraparound included, because the C comment's argument that it can't overflow is now something a proof has to check.

Then comes the property. This one ties the C fast path, the slow path over Python integers, and the dispatcher between them to a single exact count. A slow path that returned zero for big arguments fails it, and so does a fast path that always reported overflow.

theorem rangeLengthExact_proven : RangeLengthExact
-- for every start, stop, and step ≠ 0:
--   get_len_of_range on C longs is the true number of elements,
--   the long fast path returns it exactly when it fits in a long,
--   the PyLong slow path and the dispatcher always return it.

The pipeline

Every row goes through the same five gates. The funnel below is the whole project as of this snapshot. The drop between "modelled" and "reviewed faithful" is the point of the exercise.

  1. InventoryA script lists every function, opcode and grammar rule in the 3.15.2 tree. A row counts as covered only through a registry entry whose theorem unfolds that function's body.
  2. MirrorThe model follows the source in branch order. Python callbacks are fallible code that can raise, mutate state and re-enter. Py_ssize_t narrowing and C fast paths are modelled as written, and floats go through an exact IEEE-754 binary64 model.
  3. DifftestBefore any proof, the Lean model and python3 3.15.2 run side by side on generated inputs: 0, ±1, sys.maxsize, ±263, huge ints, hooks that raise. The model must agree on at least 50,000 cases over several seeds.
  4. Prove or refuteProperties quantify over all inputs. sorry, native_decide and new axioms are rejected by the build. A false statement is refuted in Lean with a concrete witness, never weakened until it becomes provable.
  5. ReviewA separate agent that didn't write the model judges each row against the source and probes each claim on the real interpreter. FAITHFUL rows count. HOLLOW rows are withdrawn until they're fixed.

The wrong-function test

The first attempt asked agents for breadth: model every function and prove at least one property about each. They did, and an independent review then found that fewer than half the rows it checked held up. In functools.py it was 21%. The theorems were true; they just didn't say anything.

A proof can be correct and still false

A Lean proof guarantees that a theorem follows from the model. It says nothing about whether the model is CPython. Several proven theorems turned out to be false about the interpreter, each caught by running the exact statement on python3 3.15.2. These were the most instructive failures.

The cache that needed sixteen terabytes

The model of the C json encoder assumed every allocation succeeds. So its theorem promised that the indent cache gets built for any nesting depth up to about 245, including one where the string alone would take 16 TB. CPython raises MemoryError. In the fix, malloc is an oracle. The theorem now holds for every allocator, says exactly what a refused allocation does, and claims success only when the allocator grants it.

Nine frames that exist only once

A proven bound said the pure-Python pickler needs at most 10·depth + 18 interpreter frames. On a fresh interpreter, the first protocol-0 string triggers a codec lookup that imports a module and costs nine more. After that the codec is cached and the bound holds again. The difftest never saw it, because its harness had already warmed the codec. The theorem went back to open, with a note that the missing piece is a model of the codec cache.

except TypeError also catches subclasses

Three separate models, for set, enum and json, compared an exception's class name, while Python's except and C's PyErr_ExceptionMatches accept any subclass. Each produced a proven theorem that a TypeError subclass refutes. The models now carry a real exception hierarchy with multiple bases. They keep C's exact-type checks (Py_IS_TYPE) apart from its subclass checks.

A table that was freed and came back

The set model gave every hash table an identity that was never reused. That made a theorem about lookups restarting after __eq__ mutates the set provable, and false. In CPython the allocator can hand a smaller table back at the same address, so the pointer comparison after __eq__ concludes that nothing changed. We modelled address reuse and the stale bytes left past the end of the new table. That turned the proof into a refutation, and the refutation into a bug report.

What it found

When a refuted property is CPython's fault rather than the model's, it becomes a bug record. Each record has:

  • a script that prints REPRODUCED on 3.15.2, also checked against the development branch;
  • a search of the CPython tracker for duplicates;
  • an honest priority from P1 to P5, and a note on whether the behaviour might be intended.

Most findings are small. They're the kind of behaviour that only shows up once someone writes down exactly what a function does.

The two picklers stop at different depths

The C pickler is bounded by the C stack, the pure-Python one by sys.getrecursionlimit(). A list nested 400 deep pickles in C and raises in Python. This one has been open on the tracker since 2008.

v = []
for _ in range(400): v = [v]
pickle.dumps(v, 5)    # fine
pickle._dumps(v, 5)   # RecursionError

random.Random swallows class keywords

Random.__init_subclass__ accepts **kwargs and never calls super().__init_subclass__. A mixin listed after Random never has its hook run, and unknown class keywords pass silently.

class After(random.Random, Mixin): pass
# Mixin.__init_subclass__ never runs
class Kw(random.Random, flag=1): pass
# accepted; plain classes raise TypeError

An enum alias that silently binds nothing

Enum._add_value_alias_ builds its "already bound" error inside a try whose except TypeError was meant for unhashable values. If a __repr__ raises TypeError while that message is formatted, the conflict is swallowed and the call returns None.

class W(Enum):
    A = 1; B = 2
    def __repr__(self): return 5
W.B._add_value_alias_(3)
W.A._add_value_alias_(3)  # None, not ValueError

An ignored = still counts as padding

binascii.a2b_base32 gained ignorechars in 3.15. With = in it, the base64 decoder resets its padding count after a data character and the base32 decoder doesn't, so the position of an ignored = changes the result.

a2b_base32(b"AAAAAAA",  ignorechars=b"=")
# Error: Incorrect padding
a2b_base32(b"AAAA=AAA", ignorechars=b"=")
# b'\x00\x00\x00\x00'

{{MEMSAFE}} of the records are memory-safety bugs: use-after-free and out-of-bounds access reachable from pure Python, almost all through a callback that mutates a container while C code still holds a pointer into it. CPython doesn't treat running untrusted Python code as a security boundary, so these are ordinary bugs. We are reporting them on the CPython tracker alongside this post. Every record, with its reproducer, is in the repository's bugs/ folder.

Related work

Formal models of real languages have a long history. What's new here is the combination: a model of the actual implementation rather than an idealized language, differential testing against that implementation, and AI agents doing the bulk of the modelling under a review process designed to catch them cutting corners.

julia-in-leanThe direct inspiration. Julia Base modelled in Lean 4, docstring promises turned into theorems, models checked by differential testing, and more than 400 bugs recorded, 75 filed after manual filtering. Its finding that 128 of 130 quick "proofs" had assumed the index was in bounds shaped our review rules.1
PTX in LeanTwo recent Lean formalizations of NVIDIA's PTX instruction set, used to prove GPU kernels correct, including FlashAttention and an MoE pipeline. Earlier, NVIDIA's own axiomatic PTX memory model was checked in Alloy and Coq.2,3,4
Python semanticsλπ ("Python: The Full Monty") gave a tested small-step semantics for a core of Python. Guth's K semantics of Python 3.3 is executable and tested against unit suites. Both model the language; this project models CPython's code, C included, function by function.5,6
JavaScript, WasmJSCert mechanized the ECMAScript specification in Coq. KJS gave a complete JavaScript semantics in K, tested against conformance suites. WebAssembly's specification was mechanized and its type system proven sound in Isabelle, which uncovered errors in the spec itself.7,8,9
Verified systemsCompCert and seL4 set the bar for proving a real implementation correct end to end. This project is far from that. It models an existing implementation rather than building a verified one, and its models are tested, not derived.10,11
Differential testingRunning two implementations on the same inputs and treating disagreement as a finding goes back to McKeeman, and Csmith showed how far it can go against real compilers. Here it gates every model before any proof starts.12,13

Do this for your language

Nothing here is specific to Python. Any project with a reference implementation, a way to run it, and a list of its functions can be modelled this way: a language runtime, a standard library, a parser, a codec, an ISA. These are the rules that made the difference, in the order we learned them.

  1. Pin one version. Model exactly one release and cite its line numbers. When the target moves, re-check every function whose body changed.
  2. Inventory everything first. List every function and count coverage against that list. Exclusions need a written reason that a reviewer can reject.
  3. Mirror, don't specify. A model that restates what a function should do will agree with the docs and miss the bugs. Copy the branch order, the early returns and the error messages.
  4. Make callbacks fallible. Model user code as something that can raise, mutate the world and re-enter. Most memory-safety bugs live on those paths.
  5. Difftest before you prove. Proving things about a wrong model wastes the proof. Reach 100% agreement on edge-heavy inputs first.
  6. Refute, never weaken. If a statement is false, prove it false with a witness and keep the record. Narrowing it until it becomes provable hides exactly the case you were looking for.
  7. Run the exact statement against the real thing. A correct proof of a false theorem is the most dangerous output this process can produce.
  8. Review with the wrong-function test. Have someone who didn't write the theorem ask what broken implementation would also satisfy it. Count only what survives.

The project's working documents are written to be reused. Point your own agents at them, replace CPython with your target, and keep the rules.

  • AGENTS.mdThe playbook every modelling agent follows: rules, layout, forbidden tactics, what review keeps rejecting.
  • coverage/REVIEW_PROMPT.mdThe independent review, including the wrong-function test and the FAITHFUL / HOLLOW verdicts.
  • coverage/methods/The inventory: one row per function, opcode and grammar rule, with status and the entry that covers it.
  • difftest/Generators and the harness that run the Lean model and CPython side by side.
  • bugs/One YAML file per finding: reproducer, cause with line numbers, duplicate search, priority, possible fix.
  • lean/PyLean/The models and proofs, one directory per area of CPython.

What is left

Most of CPython. The standard library written in Python is the largest area and the least covered. Concurrency is out of scope: blocking calls are modelled single-threaded. Garbage-collector traversal is excluded by policy, because there is no heap model. Every open property carries a note saying what is missing, so the gaps are written down where the next person will look.

The rule stays the same as the work grows. A function counts only when its model mirrors the source, its theorem would catch a wrong implementation, and a reviewer who didn't write it agrees.
